# FlexiWalker API Guide for Developers

This guide explains how to implement new random walk workloads in FlexiWalker. The framework is designed to make it easy to add new walk algorithms with minimal boilerplate.

## Quick Start: Adding a New Walker

To add a new random walk workload, you need to:

1. Define a walker class in `include/app.cuh`
2. Implement **only two required methods**: constructor and `get_weight()`
3. Optionally override `is_stop()` (defaults to fixed-length walks) or `update()`
4. Add a `DEFINE_bool` flag in `src/main.cu` and a matching `DECLARE_bool` at the top of `src/walk.cu`
5. Add an else-if branch to **all three** dispatch chains in `src/walk.cu` (`profile_current_walker`, `walk_test`, `walk_batch`)
6. Run the compilation pipeline to generate optimized code
7. Build and test

## Walker Class API

### Minimal Required Interface

Every walker class must inherit from `WalkerMeta` and implement:

```cuda
class MyWalker : public WalkerMeta {
 public:
  // 1. REQUIRED: Default constructor
  MyWalker() {}

  // 2. REQUIRED: Initialization constructor with LLVM_CTOR decorator
  //    Add your custom parameters after max_depth
  LLVM_CTOR MyWalker(gpu_graph* _graph, int _max_depth, /* your params */)
      : WalkerMeta(_graph, _max_depth) {
    // Initialize your parameters here
  }

  // 3. REQUIRED: Compute edge weight for sampling
  //    - task: Current walk state
  //    - i: Index of neighbor (0 to task->degree-1)
  //    - Return: Weight for this edge (0.0 means skip this edge)
  __device__ weight_t get_weight(Task* task, int i) {
    // Your weight computation logic
  }

  // 4. OPTIONAL: Override to customize walk termination
  //    DEFAULT: Stops when len >= max_depth (fixed-length walks)
  //    Only implement if you need probabilistic or conditional termination
  template <typename state_t>
  __device__ bool is_stop(int len, state_t* state) {
    // Your custom termination logic
    // Most walkers use the default and don't implement this
  }

  // 5. OPTIONAL: Custom task update after selecting next vertex
  //    DEFAULT: Task::update() handles standard state transitions
  //    Only needed for special cases (e.g., modifying graph, extra state)
  __device__ void update(Task* task, vtx_t selected_id) {
    // Your custom update logic
  }
};
```

**That's it!** Only the constructor and `get_weight()` are required. The rest have sensible defaults.

### Standard Template Methods

These methods have standard implementations that work for all walkers. Simply copy them as-is into your walker class:

**Scan method** - Check for positive-weight edges (copy as-is):
```cuda
__device__ bool scan_thread(Task* task) {
  vtx_t size = task->degree;
  for (int i = 0; i < size; i++) {
    if (get_weight(task, i) > 0) return true;
  }
  return false;
}
```

This implementation is identical across all walkers — it calls your `get_weight()` method to perform the actual edge weight computation.

### Automatically Generated Methods

**DO NOT IMPLEMENT** these methods in your walker class. They are automatically generated by the FlexiWalker compiler pipeline:

- `fill_dummy()` - Fills temporary task structures (2 overloads)
- `get_max_weight()` - Computes maximum weight for optimization
- `get_sum_weight()` - Computes weight sum for sampling

Simply declare them in your class (implementations are in generated files):
```cuda
__device__ void fill_dummy(Task* task, Task* dummy_task, int lid, int target_tid);
__device__ void fill_dummy(Task* task, Task* dummy_task, int lid, int target_tid, unsigned mask);
__device__ weight_t get_max_weight(Task* task, int i);
__device__ weight_t get_sum_weight(Task* task, int i);
```

Generated files:
- `include/generated/fill_dummy.cuh`
- `include/generated/get_max_weight.cuh`
- `include/generated/get_sum_weight.cuh`

### Custom Task Types (Advanced)

The default `Task` carries `current_vertex`, `prev_vertex`, `neighbor_offset`, `degree`, and `length`. That covers most walkers — including second-order walks like Node2Vec, which only need `prev_vertex`. **Only define a custom task if `get_weight()` needs history beyond that**, for example the previous vertex's degree or neighbor offset, accumulated state across steps, or two-hop history.

The runtime templates every kernel on `walker_t::TaskType`, so the custom type flows end-to-end. The compiler pipeline's metadata extractor also picks up `using TaskType = X;` from your walker and groups walkers by task type in downstream analyses.

#### Step 1: Subclass `Task` in `include/gpu_task.cuh`

Add your class next to `Task` / `PPRSecondTask`. You need a default constructor, a walker-id constructor that delegates to `Task`, and — critically — an `update()` override that snapshots your extra fields *before* calling `Task::update()` (which overwrites `prev_vertex`, `neighbor_offset`, `degree`, `length`):

```cuda
class PPRSecondTask : public Task {
 public:
  edge_t prev_neighbor_offset;
  vtx_t prev_degree;

 public:
  __device__ PPRSecondTask() : Task() {
    prev_neighbor_offset = static_cast<edge_t>(-1);
    prev_degree = static_cast<vtx_t>(-1);
  }
  __device__ PPRSecondTask(gpu_graph* graph, vtx_t _current_vertex, int _walker_id)
      : Task(graph, _current_vertex, _walker_id) {
    prev_neighbor_offset = static_cast<edge_t>(-1);
    prev_degree = static_cast<vtx_t>(-1);
  }
  __device__ void update(gpu_graph* graph, vtx_t selected_id) {
    // Snapshot old state BEFORE Task::update() overwrites it.
    prev_degree = degree;
    prev_neighbor_offset = neighbor_offset;
    Task::update(graph, selected_id);
  }
};
```

If you skip the `update()` override, your extra fields stay at their initial values for the whole walk — a silent correctness bug.

#### Step 2: Opt your walker in with `using TaskType = ...`

Once you declare the alias, **every** method signature in your walker class must use `TaskType*` instead of `Task*` — including the auto-generated method declarations. Mixing `Task*` and `TaskType*` will compile but the generated code won't link against your walker's overloads.

```cuda
class PPR_second : public WalkerMeta {
 public:
  float alpha;
  using TaskType = PPRSecondTask;  // <-- opt in

 public:
  PPR_second() {}
  LLVM_CTOR PPR_second(gpu_graph* _graph, int _max_depth, float _alpha)
      : WalkerMeta(_graph, _max_depth) {
    this->alpha = _alpha;
  }

  __device__ weight_t get_weight(TaskType* task, int i) {
    // Free to read task->prev_degree, task->prev_neighbor_offset here.
    ...
  }

  // All four auto-generated declarations must also use TaskType*:
  __device__ void fill_dummy(TaskType* task, TaskType* dummy_task, int lid, int target_tid);
  __device__ void fill_dummy(TaskType* task, TaskType* dummy_task, int lid, int target_tid, unsigned mask);
  __device__ weight_t get_max_weight(TaskType* task, int i);
  __device__ weight_t get_sum_weight(TaskType* task, int i);

  __device__ bool scan_thread(TaskType* task) {
    vtx_t size = task->degree;
    for (int i = 0; i < size; i++) if (get_weight(task, i) > 0) return true;
    return false;
  }
};
```

No other files need to change — the compiler pipeline and dispatch chains treat a custom-task walker exactly like any other walker.

## Available Data Structures

### Task Structure (`gpu_task.cuh`)

The default `Task` provides:

```cuda
class Task {
  int walker_id;              // Walker ID
  vtx_t current_vertex;       // Current vertex in walk
  vtx_t prev_vertex;          // Previous vertex (-1 for first step)
  edge_t neighbor_offset;     // Offset into graph->adjncy array
  vtx_t degree;               // Number of neighbors
  int length;                 // Current walk length
};
```

### Graph Structure

Accessible via `graph` pointer (inherited from `WalkerMeta`). The struct splits into two layers:

**Core fields** — always present:

```cuda
class gpu_graph {
  edge_t* xadj;         // CSR row pointer (size: vert_count+1)
  vtx_t* adjncy;        // CSR column indices (size: edge_count)
  weight_t* adjwgt;     // Edge weights (size: edge_count)

  __device__ vtx_t getDegree(vtx_t v);
  __device__ bool check_connect(vtx_t u, vtx_t v);
  __device__ bool check_connect(vtx_t u, vtx_t v, edge_t* offset);
};
```

**Declared fields** — appear on `graph->` only when you declare them in `config/graph_fields.config` and scope them to your walker. For example, `edge_label` is added when a walker like `Metapath` declares it:

```cuda
  int* edge_label;      // present because graph_fields.config declares it
```

See *Adding a custom graph field* below and the *Compiler Contract* section at the end of this document for how to add your own.

## Adding Your Walker to the System

### 1. Define Walker in `include/app.cuh`

Add your walker class definition with the required methods.

### 2. Run the Compilation Pipeline

Inside the toolchain container (see [Toolchain container](../README.md#toolchain-container-recommended)):

```bash
python3 run_pipeline.py --clean
```

This generates optimized code in `include/generated/`.

### 3. Add Command-Line Flag in `src/main.cu`

Near the flag definitions (around line 52):

```cpp
DEFINE_bool(MyWalker, false, "my walker description");
```

### 4. Declare the Flag for `src/walk.cu`

`DEFINE_bool` lives in `main.cu`; the dispatch chains live in `walk.cu`. gflags requires a matching `DECLARE_bool` in every translation unit that references the flag, so add one next to the existing declarations at the top of `src/walk.cu`:

```cpp
DECLARE_bool(MyWalker);
```

Without this line, the `if (FLAGS_MyWalker)` checks in the dispatch chains below fail to compile.

### 5. Add Instantiation in All Three Dispatch Chains in `src/walk.cu`

`src/walk.cu` has **three** parallel if/else dispatch chains — all three need an else-if branch for your walker:

- `profile_current_walker()` — startup kernel profile (feeds `select_algo_cost_ratio`). Uses `profile_kernels<>()`.
- `walk_test()` — the non-batch path. Uses `run_walker_test<>()`.
- `walk_batch()` — the production path (what `--all` / `--autobatch` forces). Uses `run_walker<>()`.

Missing the branch in `profile_current_walker` or `walk_test` will silently degrade or exit at startup depending on CLI flags. `profile_kernels`, `run_walker`, and `run_walker_test` have different signatures: `run_walker` takes `batch_size`, `run_walker_test` does not, and `profile_kernels` takes only the device walker pointer. All three paths that reach a timing harness also take `select_algo_cost_ratio` as the first runtime arg before your walker-specific constructor arguments.

**In `profile_current_walker()`, using `profile_kernels<>()`:**

```cpp
} else if (FLAGS_MyWalker) {
  MyWalker* walker = new MyWalker(graph_ptr, max_depth /* , your_params... */);
  MyWalker* walker_ptr = get_device_ptr<MyWalker>(walker, 1);
  ratio = profile_kernels<MyWalker>(walker_ptr);
}
```

**In `walk_batch()`, using `run_walker<>()`:**

```cpp
} else if (FLAGS_MyWalker) {
  total_time = run_walker<MyWalker>(graph_ptr, start_points, result_pool,
                                    batch_size, num_walkers, max_depth, block_num,
                                    select_algo_cost_ratio
                                    /* , your_params... */);
}
```

**In `walk_test()`, using `run_walker_test<>()`:**

```cpp
} else if (FLAGS_MyWalker) {
  total_time = run_walker_test<MyWalker>(graph_ptr, start_points_ptr, result_pool_ptr,
                                         block_num, num_walkers, max_depth,
                                         select_algo_cost_ratio
                                         /* , your_params... */);
}
```

**Examples (both sites):**

No parameters (like DeepWalk):
```cpp
// walk_batch:
total_time = run_walker<MyWalker>(graph_ptr, start_points, result_pool,
                                  batch_size, num_walkers, max_depth, block_num,
                                  select_algo_cost_ratio);
// walk_test:
total_time = run_walker_test<MyWalker>(graph_ptr, start_points_ptr, result_pool_ptr,
                                       block_num, num_walkers, max_depth,
                                       select_algo_cost_ratio);
```

With parameters (like PPR with termination probability):
```cpp
// walk_batch:
total_time = run_walker<MyWalker>(graph_ptr, start_points, result_pool,
                                  batch_size, num_walkers, max_depth, block_num,
                                  select_algo_cost_ratio, FLAGS_myparam);
// walk_test:
total_time = run_walker_test<MyWalker>(graph_ptr, start_points_ptr, result_pool_ptr,
                                       block_num, num_walkers, max_depth,
                                       select_algo_cost_ratio, FLAGS_myparam);
```

With array-typed parameters (like Metapath's schema) — the `get_device_ptr` call is needed in both sites:
```cpp
} else if (FLAGS_MyWalker) {
  int* schema_ptr = get_device_ptr<int>(schema, schema_len);
  total_time = run_walker<MyWalker>(graph_ptr, start_points, result_pool,
                                    batch_size, num_walkers, max_depth, block_num,
                                    select_algo_cost_ratio, schema_ptr, schema_len);
}
```

> **Future work.** Auto-generating this dispatch from the walker class definitions is on the roadmap — see the Roadmap section in the top-level README.

### 6. (Optional) Add Parameter Flags

If your walker needs custom parameters, add flags in `src/main.cu`:

```cpp
DEFINE_double(myparam, 1.0, "description of my parameter");
```

And add a matching `DECLARE_double(myparam);` at the top of `src/walk.cu` if you use it inside any of the three dispatch chains. Then use `FLAGS_myparam` when constructing your walker.

### 7. Build and Test

```bash
cd build
make -j

# Test your walker
./bin/flowwalker --input ../data/wiki-Vote --MyWalker --n=100
```

## Adding a Custom Graph Field

If your walker needs graph data beyond the core CSR (`xadj`/`adjncy`/`adjwgt`) — say, an extra per-edge attribute — declare it once in `config/graph_fields.config` and the pipeline will add it to `gpu_graph` for any walker that asks for it. There are three steps:

### Step 1: Declare the field and scope it to your walker

Edit `config/graph_fields.config`. The walker-scoping brackets are required — they tell the pipeline which walkers actually use this field (walkers that don't use it will not allocate memory for it):

```
# Existing example:
edge_label[Metapath,Metapath_weighted] = file:int:edge

# Your new field, loaded from a binary file, one int per edge:
edge_category[MyWalker] = file:int:edge

# Or initialized in-place to a constant, one float per vertex:
node_score[MyWalker] = init:float:node:0.0
```

Format: `<field>[<Walker>,…] = <source>:<dtype>:<scope>[:<init-value>][:preprocess=<csv>]`

- `<source>` — `file` (load from a binary) or `init` (fill with a constant)
- `<dtype>` — `int`, `float`, `weight_t`, etc.
- `<scope>` — `edge` (size = edge count) or `node` (size = vertex count)
- `<init-value>` — required if source is `init`
- `preprocess=max,min,sum` — optional; request per-vertex aggregates for monotonicity rewriting (see Compiler Contract)

### Step 2: Point each dataset's config at the file (only for `source=file`)

Edit the per-dataset config in `config/graphs/<dataset>.config` to specify where the binary lives. For example, extending `config/graphs/wiki-Vote.config`:

```
# Required: Standard graph structure
xadj = ../../data/wiki-Vote/wiki-Vote_xadj.bin
adjncy = ../../data/wiki-Vote/wiki-Vote_edge.bin
adjwgt = ../../data/wiki-Vote/wiki-Vote_weight.bin

# Your new field:
edge_category = ../../data/wiki-Vote/wiki-Vote_category.bin
```

Skip this step if the field's source is `init` — there's no file to load.

### Step 3: Use the field from your walker

After running the pipeline (step 2 of *Adding Your Walker to the System* above), the field is a member of `gpu_graph` and available to every method of walkers scoped to it:

```cuda
__device__ weight_t get_weight(Task* task, int i) {
  edge_t offset = task->neighbor_offset + i;
  if (graph->edge_category[offset] == my_target_category) {
    return graph->adjwgt[offset];
  }
  return 0.0;  // skip edges of other categories
}
```

**Important:** changing `graph_fields.config` requires rerunning the pipeline (`python3 run_pipeline.py --clean` inside the toolchain container) — the field set is baked into the generated `gpu_graph.cuh` at pipeline time.

## Tips and Best Practices

### Weight Computation

- **Return 0.0** for edges you want to skip (they won't be sampled)
- **Keep computation simple** - `get_weight()` is called frequently
- **Use graph data** - `graph->adjwgt`, `graph->adjncy`, `graph->edge_label`
- **Access task state** - `task->prev_vertex`, `task->current_vertex`, `task->length`

### Termination Logic

- **Use `myrand_uniform(state)`** for probabilistic termination (returns float in [0,1])
- **Check `len >= max_depth`** to respect max depth limits
- **Template function** - works with both `myrandStateArr*` and `curandState*`

### Custom Update (Rare)

Only implement `update()` if you need to:
- Modify graph structure during walks (edge-reinforcement-style walkers)
- Track additional per-step state in custom Task
- Most walkers DON'T need this

### Testing and Debugging

1. **Start simple** - Test with small graphs and few walkers
2. **Use printresult** - `--printresult` flag to see walk paths
3. **Check weights** - Ensure `get_weight()` returns expected values
4. **Pipeline first** - Always run pipeline after changing walker classes

## Common Patterns

### Uniform Random Walks
```cuda
__device__ weight_t get_weight(Task* task, int i) {
  return 1.0;  // or return graph->adjwgt[...] for weighted uniform
}
```

### Conditional Edge Selection
```cuda
__device__ weight_t get_weight(Task* task, int i) {
  // Only traverse edges meeting some criterion
  if (some_condition(task, i))
    return 1.0;
  else
    return 0.0;  // Skip this edge
}
```

### Probabilistic Termination
```cuda
template <typename state_t>
__device__ bool is_stop(int len, state_t* state) {
  return myrand_uniform(state) <= probability || len >= max_depth;
}
```

### Fixed-Length Walks
```cuda
template <typename state_t>
__device__ bool is_stop(int len, state_t* state) {
  return len >= max_depth;
}
```

## Troubleshooting

### Pipeline Errors

**Error**: "Failed to extract metadata"
- Check that your walker inherits from `WalkerMeta`
- Ensure constructor has `LLVM_CTOR` decorator
- Verify `get_weight()` and `is_stop()` are present

**Error**: "Type analysis failed"
- Check that method signatures match exactly
- Ensure you're using `Task*` or `TaskType*` consistently

### Build Errors

**Error**: "undefined reference to fill_dummy"
- Run the pipeline: `python3 run_pipeline.py --clean`
- Check that `include/generated/fill_dummy.cuh` exists

**Error**: "no matching function for call"
- Check constructor parameters in `src/walk.cu` match your walker class
- Verify method signatures in your walker class

### Runtime Errors

**Error**: Walks terminate immediately
- Check `is_stop()` logic - may be returning true too early

**Error**: Walks never terminate
- Check `is_stop()` logic - ensure max_depth check is present
- Verify `len >= max_depth` comparison

**Error**: Incorrect sampling
- Verify `get_weight()` returns correct values
- Check that weights are non-negative
- Use `--printresult` to inspect walk paths

## Compiler contract

The pipeline's output depends on three inputs: your walker class (in `include/app.cuh`), the graph-fields declaration (`config/graph_fields.config`), and the monotonicity of your `get_weight`. This section documents what the compiler promises, what it needs from you, and how to tell when it has given up and fallen back to a generic code path.

### `graph_fields.config`

`config/graph_fields.config` lists the *non-core* graph fields that your walkers read. The core CSR (`xadj`, `adjncy`, `adjwgt`) is always present — you do not declare it. `adjwgt` is also auto-preprocessed into `adjwgt_MAX`, `adjwgt_MIN`, and `adjwgt_SUM` for every build; you do not declare those either.

Example (the shipped config):

```
edge_label[Metapath,Metapath_weighted] = file:int:edge
```

Each declaration has the form:

```
<field>[<Walker1>,<Walker2>,...] = <source>:<dtype>:<scope>[:<init-value>][:preprocess=<csv>]
```

- `<source>` — `file` (load from a binary file whose path lives in `config/graphs/<dataset>.config`) or `init` (fill every element with `<init-value>`)
- `<dtype>` — `int`, `float`, `weight_t`, etc.
- `<scope>` — `edge` (size = edge count) or `node` (size = vertex count)
- `<init-value>` — required iff `<source>` is `init` (e.g. `init:float:node:0.0`)
- `preprocess=max,min,sum` — optional per-vertex aggregates, each one allocating a `<field>_MAX` / `_MIN` / `_SUM` array

The walker-scoping brackets are required: a field is only materialized for the walkers listed, so walkers that don't use it pay no memory cost.

The `preprocess` list controls what `include/generated/gpu_graph.cuh` allocates:

- `max` → a per-vertex array `<field>_MAX` whose entry `v` is `max{<field>[e] : e ∈ out_edges(v)}`
- `min` → per-vertex `<field>_MIN` (analogous)
- `sum` → per-vertex `<field>_SUM`

You must declare every aggregate role your walkers need. If the compiler rewrites `get_weight` to read `<field>_MAX`, the config must include `max` for that field. The pipeline validates this and fails loudly when a role is missing.

### Monotonicity rewriting

When your walker is monotonic (its `get_weight` is non-decreasing in the preprocessed field), the pipeline can replace a per-edge `get_weight` call during `get_max_weight` with a single per-vertex lookup into `_MAX`. This cuts `get_max_weight` complexity from O(degree) to O(1) per vertex.

The pipeline analyzes your `get_weight` at the Clang AST level, propagating a "target sign" (MAX or MIN) through the expression:
- Additions preserve the sign.
- Subtractions flip the sign on the right operand.
- Multiplications and divisions preserve the sign iff the other operand is positive (the analyzer rejects unknown signs).
- Field accesses `graph-><field>[<index>]` are rewritten to `graph-><field>_MAX[<index>]` or `_MIN` based on the propagated sign.

### eRVS-only fallback

If the analyzer cannot prove monotonicity or cannot safely rewrite the expression, it marks the walker `ERVS_ONLY=1` in `include/generated/walker_traits.cuh`. The walker still runs — just via the generic exact-rejection-sampling path, not the optimized monotonic path.

Triggers:
- Non-monotonic expression (e.g. absolute value, modulo, unknown function)
- Non-canonical index into a preprocessed field — the index must be one of `task->neighbor_offset [+ loop_local]`, `task->prev_neighbor_offset [+ loop_local]`, `task->current_vertex`, or `task->prev_vertex`. Anything else (e.g. `task->neighbor_offset + 3 * i`) forces eRVS-only because the textual rewrite that converts indices post-analysis cannot handle it safely.
- Graph-mutating `update_weight` — if the analyzer detects that `update_weight` writes to the graph structure, monotonicity is not safe to assume.
- Complexity budget exhaustion — the AST walker has a depth/branch budget (see `pipeline/config.py`); expressions that exceed it trigger fallback.

How to tell: `artifacts/type_analysis.json` records a `fallback_reason` per walker branch. `include/generated/walker_traits.cuh` has an `ERVS_ONLY` entry per walker. Pipeline verbose logs (`--verbose`) print the reason at the type-analysis stage.

### Where generated files live

All pipeline output lands in `include/generated/`:
- `gpu_graph.cuh` — walker-specialized graph struct + preprocessed aggregates
- `fill_dummy.cuh` — pipeline-generated task fillers
- `get_max_weight.cuh`, `get_sum_weight.cuh` — generated aggregate functions
- `walker_traits.cuh` — per-walker flags (ERVS_ONLY, has_update_weight, …)

These are regenerated on every `run_pipeline.py` invocation; do not edit them by hand.
